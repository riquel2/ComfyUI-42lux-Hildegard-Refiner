【它是干什么的】

给 ComfyUI 的 ComfyUI-42lux-Hildegard-Refiner（Flux2 Klein 分块精修）
逐张图片生成两样东西：

  1. 该用哪个提示词（带 RFNTILE. 触发词，直接粘进 CLIPTextEncode）
  2. 该在云上怎么设节点（一份能照着填的参数清单）

本地 ComfyUI 已删除不影响使用——这个工具只做「算 + 写」，
不连 ComfyUI，图片也不会传给 ComfyUI。


【怎么启动】

双击  启动Hildegard助手.bat

如果双击后窗口闪一下就没了，看同目录的 gui_start.log，里面有报错原因。


【三步用法】

1. 点「添加图片…」选一张图（可多选，左边会出现列表）

2. 看右边：
   · 关键数字区 —— 输出尺寸 / 网格 / 块数 / 档位，参数一改就重算
   · 试算表 —— 列出 9 种 tile 尺寸各自的结果，**双击某行就套用**
   · 参数区 —— tile 尺寸 / 最小重叠 / min_scale_factor 等
   · 参数区最后那行暖色字 —— 「精细度：tile 2048 → 每遍 4.19 MP →
     偏大偏平滑」**会跟着 tile 实时变**，是给眼睛扫的
   · 「精细度」页 —— 哪些参数真的影响精细度、哪些不影响，实时重算
     （见【cell_size 和 ctrl3_max_size 会影响精细度吗】）
   · 「ComfyUI 设置说明」页 —— 照着这份清单在云上设节点

3. 点「生成提示词」→ 等 10~60 秒 → 点「复制提示词」→ 粘进 ComfyUI

   提示词框上方会有一行小灰字，跟着「参考形态」和「档位」实时变：
     · 三参考 + full_build 档 → 「Image 1/2/3 = 块本身 / 位置图 / 全图缩略
                                  （不是图片列表）」
     · 三参考 + texture / subject_less 档
                            → 「本档提示词没有 Image 编号（只在 full_build
                                档出现）」
     · 单参考               → 「单参考：提示词里不出现 Image 编号」
   这行是给你确认「提示词里那几个 image 是什么、现在到底有没有」用的，见
   【提示词里的 Image 1 / Image 2 / Image 3 是什么】。

4. 看提示词**下方**有没有弹出橙色底的自检面板。

   如果模型漏填了 md 规定「Always」的块（最容易漏的是第 4 块特殊材质，
   它是 md 标的 core slot），状态栏会写「生成完成，但有 N 条自检提醒」，
   提示词下面会多出一块面板，逐条说明缺的是第几块、缺了会有什么后果。
   实拍见 界面预览-自检提醒.png。

   ⚠ 这块面板**不属于提示词**。旧版本是把提醒直接接在提示词正文末尾的，
   结果是「复制提示词 / 导出 txt」会连中文提醒一起带走 —— 粘进
   CLIPTextEncode 的就不再是 md 原文了。现在提醒走独立面板，提示词正文
   永远等于模板组装出来的那一段，一个字都不多。自检 [15] 专门守这条。

   看到提醒怎么办：回「精细度」页补上对应内容，再点一次「生成提示词」。
   提醒消失后提示词区会自动收回全部高度。


【字太小看不清怎么办】

右上角有个「字号」下拉，四档：小 / 标准 / 大 / 特大。
默认是「标准」，换完立刻生效，并记进 config.json，下次打开还是这个字号。

  小 10pt · 标准 12pt · 大 14pt · 特大 16pt

为什么没有更大的档？因为你这台屏是 3200×2000、显示缩放 200%，
程序会再按 DPI 把字放大一倍——「大」实际渲染出来已经是 37px 高的字，
比 Windows 系统界面文字还大一圈；再往上加，窗口高度就装不下内容了。
真觉得不够，去「设置 → 系统 → 显示 → 缩放」调大系统缩放更合适。

字号调大时，界面会自动做三件事，不用你操心：
  · 预览图跟着缩小，把纵向空间让给文字
  · 窗口按 DPI 放大（不是简单拉伸，字是清晰的）
  · 参数区、试算表、提示词框的高度自动重排，不会互相挤掉

如果还是觉得挤，直接把窗口拖大（或最大化）即可，
提示词框会自动跟着变高。


【参数不是各管各的——它们是联动的】

参数区那几个下拉不是独立的旋钮，它们合起来决定同一组结果：

    tile 尺寸 ┐
    最小重叠  ├─→ 输出尺寸 → 网格 / 块数 ─→ 提示词档位
   min_scale ┘                            └─→ 云上采样次数（= 费用）

所以改任何一个，工具都会立刻重算并刷新这三处：

   · 关键数字区（输出尺寸 / 网格 / 实际倍数 / 重叠像素 / 档位）
   · 试算表（9 种 tile 尺寸的结果，用的就是你当前的「最小重叠」）
   · ComfyUI 设置说明

谁影响谁：

   tile 尺寸         → 输出尺寸、块数、档位、每块的实际分辨率
   最小重叠          → 输出尺寸、块数、档位（见【最小重叠是什么】）
   min_scale_factor  → 只是下限，实际倍数会被上面两者决定的刻度吸附
   参考形态          → 不影响尺寸，但同时影响**提示词**和**设置说明**：
                       提示词（三参考点名 Image 1/2/3 / 单参考只说 this image）
                       设置说明（三参考写 × 3 / 单参考写 × 1 并标出不接哪两路）
                       ⚠ 它必须跟你 ComfyUI 里**实际接了几路参考**对上，
                       详见【三参考和单参考有什么区别，怎么选】；
                       三参考 + full_build 档（≤6 块）时提示词里会出现
                       Image 1/2/3 —— 指的是这一个块的三路参考，
                       **不是**你的图片列表，详见
                       【提示词里的 Image 1 / Image 2 / Image 3 是什么】
   cell_size 等      → 只进 ComfyUI 设置说明，不影响提示词

⚠ 唯一不会自动跟着变的是**已经生成好的提示词**。

   档位是按块数判的。你把 tile 从 1536 调到 1024，块数可能从 2 变 8，
   档位就从 full_build 掉到 texture——这时候旧提示词是错的：
   它还在逐元素点名材质，而新网格里的每块已经装不下主体了。

   工具会提醒你：一旦参数改动让提示词过期，
   「提示词」页签的标题会变成「提示词 ⚠ 参数已改」，
   底下状态栏也会写「参数已改，提示词可能过期——请重新生成」。
   看到就点一次「生成提示词」。


【tile 尺寸是什么（新手必读）】

AI 一次能处理的画面有上限，所以要「切块」：把放大后的图切成一个个
正方形小块，每块单独送给 AI 处理，最后再拼回整图。
这个正方形小块的边长，就是 tile 尺寸。

   填 2048 = 每块 2048 × 2048 像素

那为什么改 tile 尺寸，输出尺寸也跟着变？
因为算法有个硬约束：输出尺寸必须能被整块拼出来。
宽度只能等于「tile宽 × 块数 − 重叠 × (块数−1)」，
也就是只能落在整块的格点上。tile 越大，格点越稀疏，倍数就只能往上跳。

同一张 1024×1536 的图，只改 tile 尺寸
（下面这组数字是在「最小重叠 = 1/4 Tile」下算的。重叠一改，数字就跟着变，
  见后面【最小重叠是什么】——它和 tile 尺寸一样是决定输出尺寸的参数）：
   tile 1024  →  输出 1792×2688  (1.75×)  切成 2×4 =  8 块
   tile 1536  →  输出 1536×2304  (1.50×)  切成 1×2 =  2 块
   tile 2048  →  输出 2048×3072  (2.00×)  切成 1×2 =  2 块
   tile 2560  →  输出 2560×3840  (2.50×)  切成 1×2 =  2 块
   tile 3048  →  输出 3040×4560  (2.97×)  切成 1×2 =  2 块

怎么选（官方示例工作流的便签原文：「Tile Sizes: 1024×1024 up to
3048×3048」；节点本身允许 16 ~ 8192，步长 16）：

   ⚠ 先把两个完全不同的问题分开：
     · 「工具默认为什么是 2048」—— 为了让工具算出来的块数 / 档位和你
       手上那套工作流一致（那边 PrimitiveInt 填的就是 2048）。这是
       **对齐**，不是画质推荐。详见下一节开头的说明。
     · 「画质该用多少」—— 比 2048 小。2048 是各档里**每块画布最大**的
       一档（4.19 MP），而采样只有 4 步，所以出图偏平滑。

   · 想要更精细 → 1536 ~ 1792（下一节有按「每遍画布」排序的对照表）
   · 想省时间省钱 → 调大（块数少 = 采样次数少 = 云上更便宜）
   · 输出长边别超 8000 太多，块数会爆炸

⚠⚠ 一个很容易被骗到的地方：官方示例工作流里 `Hildegard Plan` 节点上
   显示的 tile 是 **1536**，但那两个数字是**死值**。

   实测（读 example_workflows/42lux-hildegard-refiner.json 的连线）：
     Hildegard Plan 的 tile_width  ← PrimitiveInt 节点，值 2048
     Hildegard Plan 的 tile_height ← PrimitiveInt 节点，值 2048
   在 ComfyUI 里，输入一旦被连线，节点上那个 widget 就被忽略。
   所以官方示例的**实际 tile 是 2048**，不是它显示的 1536。

   自证：同一条链上 EmptyLatentImage 的宽高也来自同两个 PrimitiveInt
   （2048）。如果 tile 真是 1536 而采样画布是 2048，Hildegard Combine
   的尺寸就对不上、根本拼不回去——所以实际一定是 2048。

   所以：
     · 你工作流里若用 PrimitiveInt 连了 tile_width / tile_height，
       以 **PrimitiveInt 的值**为准，别信 Plan 节点上显示的数字；
     · 本工具默认按 2048 算，和你手上这套工作流一致。

   官方示例里这两个 PrimitiveInt 就是 **#25（→ tile_width）** 和
   **#24（→ tile_height）**。**要改 tile 尺寸，就改这两个节点的「数值」**，
   而且两个必须改成同一个值：

     #25 还同时驱动 EmptyLatentImage.width 和 Flux2Scheduler.width
     #24 还同时驱动 EmptyLatentImage.height 和 Flux2Scheduler.height

   也就是说，改它们会一并把「采样画布」和「调度器分辨率」改对，
   别的节点不用动 —— 这正是这两个节点存在的意义。
   反过来，只改其中一个的话 tile 就变成长方形，网格和位置参考图都会变怪。

   ⚠ 顺带一个巧合：如果你把这两个都改成 1536，Plan 节点上那个一直显示
     1536 的 widget 就**碰巧变成真的了**。所以「1536 还是 2048」这个
     困惑，改成 1536 之后就自动消失了 —— 但你仍然应该以这两个节点的
     数字为准，而不是以 Plan 节点显示的数字为准。

   ⚠ 而 Plan 节点上的另外四个参数（`1/4 Tile` / `1.3` / `spiral` /
     `lanczos`）**没有连线，是真正的活值**，直接在 Plan 节点上改。

⚠ 一个连带影响：块数决定了提示词档位。
   同一张图，tile 大 → 块少 → 走 full_build 档（逐元素点名材质）；
   tile 小 → 块多 → 自动退到 texture / subject_less 档（只做材质普查、
   甚至去掉主体名）。所以改完 tile 尺寸，记得重新生成一次提示词。
   （下面举的那张 5970×3840 的图就是个现成例子：tile 2048 是 15 块 →
   texture 档，tile 1280 就变成 40 块 → subject_less 档。）


【tile 越小细节就越好吗？——方向对，但「越小越好」是错的】

── 先澄清一件事：工具为什么默认 2048 ──

**不是因为 2048 画质最好，是为了「对齐」。**

官方示例工作流里 Plan 节点显示的 1536 是**死值**，真正的 tile 由两个
PrimitiveInt 决定，值是 2048（见【tile 尺寸是什么】）。工具默认跟着
2048 走，算出来的块数 / 档位 / 输出尺寸才和你 ComfyUI 里实际跑的一致。

**但画质上，2048 恰恰是最差的那一档之一**：它是所有档位里「每块画布」
最大的一档（4.19 MP），而采样只有 4 步 —— 每像素分到的去噪预算最薄，
所以出图偏平滑、偏塑料感。

   对齐用 2048 ≠ 画质用 2048。**要更精细就往 1536 ~ 1792 走。**

── 画质排序表（按「每遍画布」从小到大排）──
源图 5970×3840、min_overlap 1/4、min_scale 1.3：

   tile   一遍画布   每块覆盖源图   输出          倍数    块数   生成总量
   1024   1.05 MP    698 px       8756×5632    1.47×    84    88.1 MP
   1280   1.64 MP    960 px       7960×5120    1.33×    40    65.5 MP
   1536   2.36 MP   1182 px       7761×4992    1.30×    28    66.1 MP
   1792   3.21 MP   1181 px       9054×5824    1.52×    28    89.9 MP
   2048   4.19 MP   1536 px       7960×5120    1.33×    15    62.9 MP  ← 工具默认
   2304   5.31 MP   1536 px       8955×5760    1.50×    15    79.6 MP
   2560   6.55 MP   1536 px       9950×6400    1.67×    15    98.3 MP
   2816   7.93 MP   1536 px      10945×7040    1.83×    15   118.9 MP
   3048   9.29 MP   2201 px       8270×5320    1.39×     8    74.3 MP

「一遍画布」那一列才是画质排序：**2048 及以上都在 4.19 MP 以上，
是画质最差的一段。**

出图最细的是 1024（1.05 MP），但 84 块太贵。同价位（都是 28 块）的
两个选择：

   · **1536** —— 每遍画布最小（2.36 MP，比 2048 小 44%），出图最锐。
     代价：输出反而小一点（7761×4992 = 38.7 MP），倍数最低（1.30×）。
     **想要「更精细」优先试这个。**
   · **1792** —— 每遍画布 3.21 MP（比 2048 小 23%），输出最大
     （9054×5824 = 52.7 MP，比 2048 大 29%），倍数更高（1.52×）。
     代价：画布比 1536 大。

── 那为什么不是「越小越好」到 1024 ──

「一遍画布」这一项确实是 1024 最好（1.05 MP）。但小 tile 有四个反向的
代价，而且它们是**一起**变坏的：

   tile   一遍画布   块数   缝段   羽化带   真淡入   每块能看到
   1024   1.05 MP    84    149     80 px   34 px   画面宽的 11.7%
   1280   1.64 MP    40     67     81 px   36 px   画面宽的 16.1%
   1536   2.36 MP    28     45    124 px   44 px   画面宽的 19.8%
   1792   3.21 MP    28     45    145 px   48 px   画面宽的 19.8%
   2048   4.19 MP    15     22    142 px   46 px   画面宽的 25.7%

   1. **缝段数暴涨**：1024 有 149 段缝，2048 只有 22 段 —— 6.8 倍。
      每段缝都是两次独立渲染的交界，也就是一处色带机会。
   2. **每条缝的羽化带变窄**：1024 / 1280 只剩 80 px 左右，真交叉淡入
      34 ~ 36 px，掉进前面说的「硬缝危险区」；1536 以上是 44 ~ 48 px。
      想把羽化带补回来就得把重叠提到 1/2 —— 那 1024 会变成 **135 块**，
      代价再翻一倍。
   3. **每块看到的画面越来越少**：1024 时单块只占画面宽的 11.7%，
      模型容易「不知道自己画的是什么」→ 内容漂移、串味风险最高。
      这正是档位自动退到 subject_less（去掉主体名）的原因 ——
      而**去掉主体名本身也是画质损失**：提示词给模型的锚点变少了。
   4. **总耗时**：84 块 ≈ 2048 的 5.6 倍。

所以「画质最好」不是「每遍画布最小」，而是**两股力的平衡点**：

   局部锐度  ←── 小 tile 更好（每遍画布小，模型在舒服的分辨率上画）
   全局一致  ←── 大 tile 更好（缝少、上下文多、档位更具体）

对这张图，平衡点在 **1536 ~ 1792**（都是 28 块、45 段缝、每块能看到
约 20% 画面宽）。1024 不是「画质最好」，是「**局部最锐、全局最差**」。

⚠ 想验证「再小一点是不是还更好」，别直接跳到 1024（84 块很贵）。
   先试 **1280**（40 块、1.64 MP）：如果它相对 1536 没有明显更锐，
   或者接缝 / 色带开始露出来，那 1024 只会更糟。

── 机制一：tile 尺寸就是「模型每一遍要画的画布」──
采样器不是「给原图加噪再改」，而是**从纯噪声重画一整块**，画布就是
tile 那么大。你这条链上 Flux2Scheduler 的 steps = 4，所以每一遍只有
4 步，画布越大，每像素分到的去噪预算越薄：

   tile 1024  →  一遍要画 1.05 MP
   tile 1280  →  一遍要画 1.64 MP
   tile 1536  →  一遍要画 2.36 MP
   tile 1792  →  一遍要画 3.21 MP
   tile 2048  →  一遍要画 4.19 MP
   tile 3048  →  一遍要画 9.29 MP

扩散模型大致在 1 MP 上下训练，画布越大越吃力。所以 tile 小 → 模型在
它舒服的分辨率下工作 → 细节更扎实、更不容易糊成一张光滑的塑料面。
这就是「小 tile 细节好」的真正原因，对你现在「塑料感重」的毛病尤其对症。

── 机制二：tile 越小，放大倍数越高 ──
倍数 ≈ tile 尺寸 ÷ 每块覆盖的源图像素。tile 小 → 同一块画布要盖住
更少的源图像素 → 模型被要求「画」出更多东西 → 细节上限更高。

── 但 tile 和「输出尺寸 / 块数 / 档位」是绑死的 ──
这是最反直觉的一点：输出尺寸不随 tile 单调变化，它会被网格吸附。
下面拿一张 5970×3840 的源图做例子（最小重叠 1/4、min_scale 1.3）：

   tile   输出            倍数    网格   块数  一遍画布   档位
   1024   8756×5632      1.47×  12×7    84    1.05 MP   subject_less
   1280   7960×5120      1.33×   8×5    40    1.64 MP   subject_less
   1536   7761×4992      1.30×   7×4    28    2.36 MP   subject_less
   1792   9054×5824      1.52×   7×4    28    3.21 MP   subject_less
   2048   7960×5120      1.33×   5×3    15    4.19 MP   texture
   2304   8955×5760      1.50×   5×3    15    5.31 MP   subject_less
   2560   9950×6400      1.67×   5×3    15    6.55 MP   subject_less
   2816   10945×7040     1.83×   5×3    15    7.93 MP   subject_less
   3048   8270×5320      1.39×   4×2     8    9.29 MP   texture

⚠ 这张表是在**最小重叠 = 1/4 Tile** 下算的。重叠一改，整张表都不一样
  （见下一节【最小重叠是什么】）—— 这也是为什么工具里的「最小重叠」
  必须和 ComfyUI 里 Plan 节点上的一致，否则块数、档位、输出尺寸全错。

看四件反常的事：
   · **1280 和 2048 给出完全一样的输出（7960×5120、1.33×）**，但 1280
     要跑 40 块、2048 只要 15 块 —— 选 1280 是白花 2.7 倍的时间。
   · 1536 和 1792 都是 28 块，但**各赢一半**：1792 的倍数更高
     （1.52× vs 1.30×）、输出更大（9054×5824 vs 7761×4992）；
     而 1536 的每遍画布更小（2.36 vs 3.21 MP），对「模型画得稳不稳」
     更有利。要「输出更大」选 1792，要「出图更锐」选 1536。
   · 1536 的输出（38.7 MP）**比 1280（40.8 MP）还小**。tile 调大不等于
     输出变大 —— 两者被同一套格点约束卡着。
   · 1024 的输出（49.3 MP）和倍数（1.47×）都不差，但代价是 **84 块**。

所以正确的做法不是「按 tile 一格一格试」，而是**看输出尺寸有没有重复**：
同一个输出尺寸出现两次时，永远选块数少的那个。工具界面上的「试算表」
就是这张表，双击某行可直接套用。

── 代价有三条 ──
   1. 块数 = 采样次数。块多一趟就多一次「4 步 × 一整块画布」的开销。
   2. 块越多，要拼的缝越多。本流程 Combine 是「后画的盖住先画的」
      （source-over，不是加权平均），羽化带只有 overlap/4 宽，
      块与块之间那点色差不会被抹平 —— 缝多 = 出现**色带**的机会多。
   3. 每块装的内容变少，少到一定程度模型就不知道自己在画什么，
      提示词档位会自动退到 texture / subject_less（去掉主体名）。
      所以改完 tile 一定要**重新生成一次提示词**。

── 下限在哪 ──
官方示例工作流的便签写「Tile Sizes: 1024×1024 up to 3048×3048」；
节点源码里 tile_width / tile_height 的默认值就是 1536，允许 16 ~ 8192
（步长 16）。但低于 1024，每块内容太少，基本都会退到无主体档。

── 那到底选哪个 ──
仓库自己的建议是「宁可多跑几趟小的，别一次跳大的」：
   官方便签原文：My suggestion is to do 2 or 3 repeated lower
                 upscale passes instead of one big one.
                 Going for 2x should be safe though.
   README 原文：Prefer several smaller passes over one big jump.
   每一趟只让模型「发明」适量新细节，漂移才可控、缝才看不见。
   注意它说的是**每趟的放大倍数**（约 2×），不是 tile 尺寸本身 ——
   上面那张表里 1.3×~1.8× 正好落在这个区间。

对上面那张 5970×3840 的图，按目的分（最小重叠 1/4）：

   想省事 + 输出够大     →  2048（15 块、1.33×、40.8 MP），本工具默认
   想同时要倍数和输出     →  2816（15 块、1.83×、77.1 MP）
                             同样 15 块，比 2048 的倍数和输出都高得多
   想最省时间             →  3048（8 块、1.39×、44.0 MP）
   想每块画布小、出图更锐 →  1024，但这是 84 块（约 5.6 倍于 15 块）
                             且提示词会退到 subject_less 档
   别选 1280：和 2048 输出完全相同（7960×5120），却要 40 块
   别选 1536：和 1792 同为 28 块，倍数和输出都更低

   ⚠ 「细节最好」和「颜色最稳」在小 tile 上是打架的，但要说清楚是
     哪一种颜色问题：
       · 全局变暗（你现在这个）：每个 tile 都是独立从噪声重画，偏色是
         **每一遍都会发生**的系统性偏移，跟块数无关 —— 调 tile 治不了，
         要靠下一节的色彩锚定。
       · 色带（某几块偏得和邻居不一样）：这个才和块数有关，块越多越
         容易露。这种情况反而该**调大** tile。
     所以顺序是：先把颜色锚开起来，tile 再按「细节 / 成本」挑。

注意：改 tile 尺寸同时也会改变输出尺寸（见上一节），
「细节好」和「输出大」是两件事，别混在一起看。
（界面上的「试算表」就是这张表，双击某行可直接套用。）


【最小重叠是什么】

就是「相邻两块之间要搭多少」。两块不能刚好边对边拼上——那样接缝两侧
的模型各画各的，会留下一条明显的缝。所以让它们重叠一段，重叠区两边
都画过，最后由 Hildegard Combine 羽化融合掉。

   1/4 Tile  =  重叠宽度 = tile 尺寸的 1/4
                 tile 2048 时，重叠 = 512 px

搭得越多，接缝越软、越不容易看出来。

═══ 它和 tile 要怎么配合？═══

三个层次，一层比一层反直觉：

① 它**本来就跟着 tile 走**，因为单位是「tile 的几分之几」。
   你写 1/4 Tile，tile 从 2048 改成 1536，重叠就自动从 512 变成 384，
   不用你手动改数字。所以「要不要配合」这个问题，作者已经用单位解决了。

② 但实际重叠**不等于**名义值。算法最后会把网格凑到输出尺寸上，
   多出来的部分摊到每条缝上：
       实际重叠 = (tile × 块数 − 输出尺寸) ÷ (块数 − 1)
   所以 tile 2048 + 1/2 Tile 时，实际重叠是 1063 px 而不是 1024；
   甚至选 None 也不是真的 0 —— 网格凑不齐时它照样会有几十到上百像素。
   **要以 Plan 节点下方打印的那行「Overlap: …」为准。**

③ 它**独立决定输出尺寸、块数、和提示词档位**。这一层和 tile 是
   平级的两个输入，不是附属关系。下面这张表就是证据。

⚠ 但它不只影响接缝——**它和 tile 尺寸一样，会改变输出尺寸和块数。**
   这是最容易被忽略的一点，下面说清楚。

算法有个硬约束（和 tile 尺寸用的是同一个）：输出宽度只能落在
「块数 n」对应的格点上，而格点位置是

     输出宽 = tile × n − 重叠 × (n − 1)

重叠变了，整条格点阶梯就整体挪位置。于是：

   · 刻度间隔 = tile × (1 − 重叠比例) ÷ 源图短边
     重叠越大 → 间隔越小 → 刻度越密
   · 你填的 min_scale_factor 会落到哪一级，可能因此改变

实测一（源图 1024×1536，tile=2048，min_scale_factor 填 4.0）：

     最小重叠      输出          网格      块数
     None        4096×6144     2×3       6 块
     1/64 Tile   6080×9120     3×5      15 块
     1/32 Tile   6016×9024     3×5      15 块
     1/8  Tile   5632×8448     3×5      15 块
     1/4  Tile   5120×7680     3×5      15 块
     1/2  Tile   4096×6144     3×5      15 块

从 None 改成 1/64，块数就从 6 跳到 15——云上采样次数翻 2.5 倍。
这不是 bug，是刻度重排的结果。

实测二（源图 1024×1536，tile=1024，min_scale_factor 填 1.3）——
这次方向相反，重叠越大输出反而越小：

     最小重叠      输出          块数
     None        2048×3072     6 块
     1/32 Tile   2016×3024     8 块
     1/4  Tile   1792×2688     8 块
     1/2  Tile   1536×2304     8 块

实测三（源图 5970×3840，tile=2048，min_scale_factor 填 1.3）——
这张最能说明问题：

     最小重叠     名义重叠   实际重叠x   输出          网格    块数   步长   档位
     None           0        172      9552×6144     5×3     15   1876  subject_less
     1/64 Tile     32        197      9452×6080     5×3     15   1851  subject_less
     1/32 Tile     64        222      9353×6016     5×3     15   1826  subject_less
     1/16 Tile    128        272      9154×5888     5×3     15   1776  subject_less
     1/8  Tile    256        371      8756×5632     5×3     15   1677  subject_less
     1/4  Tile    512        570      7960×5120     5×3     15   1478  texture
     1/2  Tile   1024       1063      7960×5120     7×4     28    985  subject_less

三条要点：
   · **1/4 和 1/2 给出完全相同的输出尺寸和倍数（7960×5120、1.33×）**，
     但 1/2 要跑 **28 块**，1/4 只要 **15 块** —— 1/2 白花约 1.9 倍时间，
     还把档位从 texture 顶到了 subject_less。这是「重叠大一点更保险」
     这个直觉最贵的反例。
   · **重叠调小 → 输出反而更大**：None 给 9552×6144（1.60×），
     1/2 给 7960×5120（1.33×）。因为每块被吃掉的像素少了。
   · 表里有个「步长」列 = tile − 实际重叠，就是相邻两块的间距。
     1/2 Tile 时步长只有 985 px（不到 tile 的一半），等于同一片区域
     被画了两遍以上 —— 这就是块数暴涨的原因。

⚠ 所以「重叠」和「tile」的关系要这么记：
   重叠管**缝的软硬**，顺带改**输出尺寸、块数、档位**；
   tile 管**每遍的画布大小**，顺带改**倍数、块数、档位**。
   两个都会改块数，改完任何一个都要回工具重新生成提示词。

⚠ 还有一条容易漏的：**工具里的「最小重叠」必须和 ComfyUI 里
   Plan 节点上的值一致**，否则工具算出来的输出尺寸、块数、档位
   全都对不上（本工具默认 1/4 Tile，而节点自身默认是 1/32 Tile）。
   核对方法：看 Plan 节点下方打印的「Upscaled: …」和「Grid: …」两行。

所以结论是：重叠是「接缝软硬」和「输出尺寸」两个作用叠在一起的。
改完重叠，回工具里重新看一遍关键数字和设置说明。

── 到底留多宽的羽化带 ──
「缝软不软」不看名义重叠，看真正在交叉淡入的那一段有多宽。Combine
只在每条相邻边上留 overlap/4 宽的羽化带，模糊半径是 √overlap，
所以真正融合的宽度约 2×√overlap。tile 2048 下算出来是：

     最小重叠     名义重叠   实际重叠   羽化带(overlap/4)   真交叉淡入
     None           0         172          43 px            26 px
     1/64 Tile     32         197          49 px            28 px
     1/32 Tile     64         222          55 px            28 px
     1/16 Tile    128         272          68 px            32 px
     1/8  Tile    256         371          92 px            38 px
     1/4  Tile    512         570         142 px            46 px
     1/2  Tile   1024        1063         265 px            64 px

看最后两列：名义重叠从 512 涨到 1024（翻倍），真交叉淡入只从 46 px
涨到 64 px（+39%）。**这就是 1/2 Tile 性价比低的根本原因** ——
多花一倍计算量，融合带只宽了 18 px，而 √ 的收益是递减的。

反过来说，1/4 Tile 的 142 px 羽化带已经足够软了。真正危险的是
1/32 及以下：羽化带掉到 55 px 以下，真交叉淡入不到 30 px，
硬缝就会露出来。

── 「多切几块能不能换到更多精细度」──

**不能，只要输出尺寸没变。**

精细度由三件事决定，而它们**只和 tile 有关，和块数无关**：

   · 每块画布     = tile²           （2048 → 4.19 MP）
   · 每块覆盖多少源图 = tile ÷ 实际倍数（2048 ÷ 1.333 = 1536 px）
   · 每块的放大倍数 = 实际倍数       （1.333×）

1/4 和 1/2 的这三项**完全一样**，输出尺寸也一样（7960×5120）。
多出来的块全部落在「同一片源图区域被重复画了第二遍」上：

   1/4 Tile  15 块  →  生成 62.9 MP，其中 40.8 用上、22.1 被覆盖
   1/2 Tile  28 块  →  生成 117.4 MP，其中 40.8 用上、76.6 被覆盖
                        ↑ 多出的 54.5 MP 一点输出都没换到

而且副作用是反的：缝段从 22 涨到 45，处在融合带里的画面面积从
11.8% 涨到 32% —— 更多地方变成「两次渲染的合成」，**色带风险更高**。
唯一买到的是单条缝更软（羽化带 142 → 265 px）。所以只有当你确实
看到硬缝时，才值得用大重叠。

⚠ 但如果你就是愿意花 28 块，有个更好的花法 —— 同样 28 块：

   配置              输出         一遍画布   生成总像素   缝段  融合带
   tile2048 + 1/2   7960×5120    4.19 MP    117.4 MP    45   32.0%  ← 现在
   tile1792 + 1/4   9054×5824    3.21 MP     89.9 MP    45   14.8%
                    ↑ 输出+29%   ↑ 画布−23%  ↑ 省 23%          ↓ 好 54%

   同样 28 次采样、同样 7×4 网格、同样 45 段缝，但输出更大、每遍画布
   更小（对「塑料感」也更有利）、融合带更窄。**在所有维度上都更好。**
   做法：把 #25 / #24 两个 PrimitiveInt 改成 1792，Plan 的 min_overlap
   改回 1/4 Tile。（28 块 > 24，档位是 subject_less，提示词要重新生成。）

那想真正提高精细度，只有三个杠杆：

   1. **降 tile** —— 唯一直接改善「每一遍画得多细」的杠杆。每遍画布
      变小，模型回到它舒服的分辨率，出图更锐。代价是块数涨。
   2. **把每趟的放大倍数压在 ~2× 以内，宁可多跑几趟** —— 官方推荐
      「2~3 趟、每趟约 2×」。一趟跳 4~8× 时模型要凭空编太多，
      细节是编出来的而不是画出来的。
   3. **提高参考权重 / 开色彩锚** —— 让细节来自源图而不是模型的先验。
      这也是「更精细」的一部分（见【为什么会有塑料感】一节）。

   ⚠ 单独调大 min_scale_factor **不算**提高精细度：它只改输出尺寸和
     倍数，**每遍画布（4.19 MP）一点没变** —— 等于把同样的平滑度
     放大到更多像素上。实测：tile 2048 下把 min_scale_factor 从 1.3
     调到 3.0，输出从 7960×5120 涨到 19900×12800，但每遍画布始终是
     4.19 MP。要更细必须降 tile。

   **「多切几块」也不在其中。** 切块只影响「同一片区域被重复画了几遍」，
   不影响「每一遍画得多细」。

那选多少？
   · 1/4 Tile    —— 官方示例工作流的选择。羽化带 142 px，够软，块数也不失控。
                    **默认就用它**
   · 1/8 ~ 1/16  —— 想少一点重复计算时用（羽化带 92 / 68 px），接缝稍硬但可接受
   · 1/32 及以下 —— 羽化带 ≤ 55 px，真交叉淡入不到 30 px，容易看到硬缝
   · 1/2 Tile    —— 输出和 1/4 可能完全一样（见实测三），却要接近两倍的块数。
                    除非你确实在长缝上看到了色带，否则没必要

⚠ 必须注意的坑：**新建的 Hildegard Plan 节点，min_overlap 默认是
   1/32 Tile，不是 1/4**；min_scale_factor 节点默认是 3.0，不是 1.3。
   （tile 尺寸另说：官方示例里节点上显示 1536，但实际由 PrimitiveInt
   决定为 2048，详见【tile 尺寸是什么】里的「死值」说明。）
   在云上直接拖一个新节点、不逐项改，算出来的输出尺寸会和工具里的
   数字对不上。**照着「ComfyUI 设置说明」页一项一项填。**


【min_scale_factor 是什么】

它就是你「想要放大的倍数」。填 2.0 = 想把图放大到 2 倍
（注意是边长 2 倍，面积是 4 倍）。范围 1.0 ~ 8.0。

但名字里那个 min 是关键：它只是一个**下限**，不是实际结果。
算法会往上找「第一个不小于你填的值」的刻度。

刻度由 tile 尺寸和重叠共同决定。源图 1024×1536、tile 2048、重叠 1/4 时，
能落到的倍数只有这五个（换个重叠，这串数字会整体变，见【最小重叠是什么】）：

   2.0×  /  3.5×  /  5.0×  /  6.5×  /  8.0×

所以：
   填 1.00 ~ 2.00   →  实际 2.0×
   填 2.05 ~ 3.50   →  实际 3.5×
   填 3.55 ~ 5.00   →  实际 5.0×
   填 5.05 ~ 6.50   →  实际 6.5×
   填 6.55 ~ 8.00   →  实际 8.0×

两个直接推论：

1. 起步倍数 = tile 尺寸 ÷ 源图短边
   源图短边 1024 时，tile 2048 → 填 1.0 也会得到 2.0×。
   想要小于 2×，必须把 tile 调小。

2. 刻度间隔 = tile × (1 − 重叠比例) ÷ 源图短边
   tile 1024 → 间隔 0.75×（刻度密，控制精细）
   tile 1536 → 间隔 1.13×
   tile 2048 → 间隔 1.50×（刻度疏，填什么都不太跟手）
   所以选 tile 不只看细节，还要看它对「倍数控制精度」的影响。

怎么用：
   · 官方建议 2× 是安全的；不要一次跳 4~8×
   · 想精确控制倍数 → 先看试算表挑 tile，再填 min_scale_factor
   · 拿不准就填你真正想要的数，看界面显示的「实际倍数」差多少，
     再决定要不要换 tile

⚠ 注意别和 tile 尺寸搞混：
   tile 尺寸决定「刻度在哪」，min_scale_factor 决定「从哪个刻度往上找」。
   想让输出更大，调大 min_scale_factor；
   想让刻度更密、控制更细，调小 tile 尺寸。


【cell_size 和 ctrl3_max_size 会影响精细度吗】

先说结论：**两个都不是「精细度」旋钮**。
「精细度」= 每个像素能分到多少去噪预算，那个只有 tile 一个直接杠杆
（见【tile 越小细节就越好吗】）。这两个改的是别的东西：

  参数              你的值   它真正改什么                        改精细度？
  cell_size          512    位置图的分辨率（近邻环境多清楚）      ❌
  ctrl3_max_size     768    全局缩略图的长边上限（跨块一致性）    ❌


═══ 一、cell_size：你现在是对的，别动 ═══

节点源码里位置图是这样造的：画布 = cell_size × 3 见方，9 格里每一格
都是**一个 tile 大小的区域**（从放大后的图上裁），用 bicubic 缩到
cell_size × cell_size。中心格 = 当前块（带青色角标，臂长 =
0.09 × cell_size），周围 8 格 = 邻居。画布外的小格填纯灰。

所以 cell_size 改的是「模型对这个块周围环境的了解有多清楚」，
不是像素锐度。

   cell_size   位置图        每格覆盖     每格降采样   画布
      256      768×768      2048×2048       8×      0.59 MP
      384     1152×1152     2048×2048      5.3×     1.33 MP
      512     1536×1536     2048×2048       4×      2.36 MP   ← 训练默认 / 你现在
      640     1920×1920     2048×2048      3.2×     3.69 MP
      768     2304×2304     2048×2048      2.67×    5.31 MP

⚠ 一个实测出来的成本点：位置图是「每块编码一次」的。
  源码里 position_latents.append(vae.encode(pos_tensor)) 在循环内 ——
  你 28 块，就是 28 次 1536×1536 的 VAE 编码 = 66.1 MP；
  块本身的 tile_latent 是 28 × 4.19 = 117.4 MP。
  也就是说**位置图吃掉了整轮 VAE 编码量的约 36%**。

  · 想省时间/显存：cell_size 改 256 → 位置图从 66.1 MP 掉到
    16.5 MP，总编码量降约 27%，而每格仍有 8× 降采样，大概率
    看不出差别（这条是推测，值得自己 A/B 一次）。
  · ⚠ 位置图开销只跟 cell_size 和块数有关，**跟 tile 无关** ——
    把 tile 降到 1536 不会顺带省下位置图这份活。
  · ⚠ cell_size 的含义是**相对 tile 的**。tile 2048 + cell 512 =
    每格 4× 降采样；tile 1536 + cell 512 = 3× 降采样（近邻视图
    反而更细）。所以它不用跟着 tile 一起改。

结论：512 就是节点默认 + 训练默认，保持。


═══ 二、ctrl3_max_size：你的 768 比默认低 2.67 倍，但它不加细节 ═══

源码里造全局缩略图只有三行：scale = min(cap ÷ 宽, cap ÷ 高)，
scale ≥ 1 就原样返回。你放大后是 7960×5120：

   cap        全局缩略图       相对输出长边
   256        256×164            1/31      ← 节点下限
   768        768×493            1/10.4    ← 你现在
   2048       2048×1317          1/3.9     ← 节点默认 / 训练默认
   3072       3072×1975          1/2.6
   ≥7960     原样不缩（等于没接）  1

（尺寸是按 int 截断的，所以是 493 / 1975 这种尾数，不是四舍五入。）

⚠ 它确实是活的：节点 16 的 slot 4（global_latent）→
  ReferenceLatent #8 → Flux2KleinRefLatentWeight index 2、weight 0.8。
  768 → 2048 会让全局参考的线性分辨率 ×2.67、像素数 ×7.1
  （每个采样步的参考 token 大约 ×7）。

但它**不改**块画布（还是 4.19 MP）、不改输出尺寸（还是 7960×5120）、
不改块数（还是 28）、不改提示词档位（还是 subject_less）。
**所以它一个像素的细节都不会加。**

它改的是跨块一致性 / 色彩漂移 —— 就是工作流 Note 30 说的那个问题。

⚠ 这里说得保守一点：节点 tooltip 和 README 都**没写**「越大越好」的
  方向。唯一的硬事实是节点默认 2048、tooltip 写 2048 是 Hildegard
  训练默认值，而**作者自己的示例工作流填的就是 768**。
  所以 768 不是错，是作者的选择。实操：

    · 看到块间色彩漂移 → 试 2048（免费 A/B：不改输出、不加块、
      时间量级不变）。
    · 怀疑出图偏软 → 把 cap 降到 ≤1024 理论上会让模型更依赖每块
      自己的 crop。**这条是推测，没有源码或文档依据**，别当结论。


═══ 三、顺带查出一个真正的死值：low_freq_radius ═══

源码里是 if tile_high_freq_reduce > 0.0: 才去读 low_freq_radius。
你 tile_high_freq_reduce = 0 → **low_freq_radius（你填 256，
也就是上限）完全不参与计算**。它现在不影响任何东西。


═══ 四、真正提高精细度的杠杆（按性价比排序）═══

  #  杠杆                        你现在的值       怎么动
  1  tile                        2048（4.19MP）   → 1536（2.36 MP）
                                                  或 1792（3.21 MP）
                                                  唯一直接杠杆
  2  Flux2KleinRefLatentWeight   0.9 / 0.8 / 0.8  → 1.0 ~ 1.2
                                                  节点默认就是 1.0，
                                                  你三个都低于中性值
  3  tile_high_freq_reduce       0.0              已最保真，别动
  4  提示词四句 photorealistic   已有             保真方向
  5  Flux2KleinColorAnchor       mode=4（未启用） 只管色彩，不管锐度

第 2 条值得单独强调：0.9 / 0.8 / 0.8 对应
  index 0 = tile_latent      （真正的源图裁剪）
  index 1 = position_latent
  index 2 = global_latent
把 index 0 从 0.9 提到 1.0 是最直接的一步 —— 它才是「让出图长得像
源图」的那路参考，而且**零提示词风险**。

⚠ 最后：cell_size 和 ctrl3_max_size 都是**独立于 tile 的**，
  改 tile 尺寸不用动它们。


【为什么需要大模型，为什么又不需要】

参数那一半完全不需要。输出尺寸、网格、块数、档位全部由像素宽高
纯数学算出来，跟画面内容无关。工具里已经把 Hildegard Plan 的切块
算法原样移植过来了，和节点行为一致。

提示词那一半需要。因为要说出「图里有什么材质、主体是什么、光从哪来」，
这没法算。用本地 Qwen2.5-VL 或云端 API 都行。


【后端设置】

点右上角「后端设置…」。两种可切换：

◆ 本地 LM Studio（默认，推荐）
  免费、离线、图片不出本机。
  需要先把 LM Studio 打开 → Developer → Local Server → Start Server
  （默认端口 1234，与默认配置一致）。
  model 留空会自动用当前加载的第一个模型。
  你已装好 Qwen2.5-VL-7B-Instruct，直接用即可。

  ⚠ 重要：把模型的 Context Length 调到 8192。
     LM Studio 里模型卡片写着 128k，但**实际加载常常只有 4096**。
     一次请求要吃掉：指令约 2100 + 图片约 560 + 你的文字 ≈ 2700 token，
     4096 只剩 1400 给回答——很紧，容易输出半截 JSON。
     本工具已经把指令压到能塞进 4096，但调到 8192 才真正稳。

     改法（注意：**不在右侧栏**。右侧栏是「预测参数」，温度 / 限制响应长度 /
     上下文溢出都在那儿，但就是没有上下文长度——很多人在这儿找不到）：
       · 「上下文长度」属于**加载参数**。点右上角 Load Model（或聊天界面的
         模型选择器）→ 打开「手动选择模型加载参数」→ 面板里就会出现
         「上下文长度」→ 填 8192 → 加载。
       · 想一劳永逸：左侧「我的模型」→ 该模型那一行的齿轮（提示语是
         「编辑模型默认配置」）→ 加载参数 → 上下文长度 = 8192 → 保存。
         以后每次加载都是 8192，不用再管。

     别只从命令行改（lms load … --context-length 8192）——那是一次性的，
     在界面里重新加载一次就退回 4096。

     点「测试连接」会顺手探测并告诉你当前实际加载了多少，
     小于 8192 会直接提示你去调。

◆ 云端 API
  理解力更强、提示词更准，但按次付费且图片会上传。
  Anthropic 填 https://api.anthropic.com（协议选 anthropic）
  其它 OpenAI 兼容服务填到 /v1 结尾（协议选 openai）

  点「测试连接」可以立刻验证配置对不对。
  API key 会明文存在 config.json 里，别把这个文件外发。


【三个档位是怎么判出来的】

仓库给了三档模板（full_build / texture / subject_less），判断依据是
「**每块 tile 装了多少主体**」——装得多就能逐元素点名材质，装得少就只能写表面。

⚠ **不是按输入图片的像素判的。** 仓库表格里写的 "Source ≲ 2K–3K" 是**速记**：
在官方示例的 2048 tile 下（节点上显示 1536 是死值，见【tile 尺寸是什么】），
源图 2–3K 大致对应「结果 ≲4K、网格 1×1~3×2」。
真正的一级依据是**块数**，而块数是这么算出来的：

    输入像素 + tile 尺寸 + 最小重叠 + min_scale_factor
                   ↓
           算出结果尺寸和网格
                   ↓
               块数 → 档位

所以同一张源图，**你把 tile 调大，块数就少，档位会往前跳**。
输入像素只是间接因素。

判定规则（取自仓库 llm_prompt_templates/README.md 的 decision rule）：

    结果 ≲4K，网格 1×1 ~ 3×2（块数 ≤6）     → full_build
    结果 4K–8K，网格 4×3 ~ 6×4（块数 7~24） → texture
    结果 8K+（块数 >24）                    → subject_less

  两条校正（结果极大时，即使块数不多，单块也已经只是一块表面裁切）：
    结果长边 > 12000px              → subject_less
    结果长边 > 8192px 且块数 ≥12    → subject_less

  上界为什么取 24 块，而不是「结果 8K」对应的 ~35 块？因为主 README 还有一条：
    「If a pass straddles two tiers, pick the less specific one.」
    卡在两档之间时宁可选**更不具体**的那档——宁可细节少一点，也不要用点名
    主体的提示词去跑多块流程（那样会串味、会漂）。

**还有一条「像素里根本看不出来」的依据**：
  画面如果是「**密集重复主体**」（人群、羊群、贴纸阵）或「**大面积空白 /
  负空间**」，必须降到 subject_less——这两种画面点名任何主体，都会被幻觉进
  根本不含它的块里。这一条纯像素算不出来，只能看图。

  所以本工具把它交给视觉模型：模型在返回的 JSON 里填
  tier_override = "subject_less"，界面会自动改档，并在状态栏说明原因。
  改档时槽位会一起带过去（不会退回万能话）。

这些依据在代码里的位置：

    块数判档 + 结果长边校正   →  hildegard_math.pick_tier()
    内容判据（密集重复 / 空白）→  提示词里的 tier_override 字段
                                  + gui.py 的改档逻辑
    自检第 [12] 项锁住这几个边界，防止以后改坏。


【提示词的「中间那段」是怎么来的】

这是最容易误解的一点，单独说清楚。

仓库模板把提示词切成 11 个块（编号 0~10），其中：

  固定块（代码逐字写死，AI 不许碰）
     0/1  触发词 RFNTILE. + 参考说明 + 主框架
     8    clean-up（压制压缩伪影 / 色带 / 锯齿）
     9    scope lock（锁定内容与构图，必须是最后一句）

  变量块（**按你上传的这张图**，由视觉模型看图后填）
     2    主体：人 / 物件 / 场景，皮肤变体、眼睛
     3    头发（人像且头发可见时）
     4    特殊材质（核心槽位，每条 = 材质 + 子特征 + 正向守卫）
     5    精细元素（亮片、光斑、飞丝…）
     6    环境 / 背景（有背景才写）
     7    光照与调色
     10   风格 / 情绪标签（绘画类才写）

所以「中间那段是可替换的」说的就是 2~7 和 10。
本工具的做法是：**AI 只填槽位，代码负责拼句子**。

  你点「生成提示词」后实际发生的事：
    1. 代码按像素算出尺寸 / 网格 / 块数 / 档位（纯数学，不需要 AI）
    2. 把图发给视觉模型，让它返回一个 JSON（就是上面那些槽位）
    3. 代码把 JSON 塞进固定模板，拼出完整提示词
    4. 跑一遍自检（触发词在不在、scope lock 是不是最后、有没有否定式…）

  为什么要这样拆？因为固定块是 LoRA 的训练信号，被改写就失效了。
  让 AI「写一整段提示词」它一定会顺手改掉触发词和 scope lock。

  怎么确认它真的看了图？生成的提示词里应该有你这张图的具体内容
  （比如「peacock / 孔雀」「hand-painted chinoiserie wallpaper」），
  而不是一堆通用词。

  ⚠ texture 档（7~24 块）有两个专门的坑，都已经修好了，这里记一下。

  ── 坑一：模型把「材质措辞词典」当答案整段抄回来 ──

    这一档整段只有**一个**槽位，句子是

        Enrich existing textures and surfaces with … — {材质普查} — recovering …

    图是手绘壁纸（画面里根本没有皮肤、没有头发、没有嘴唇），模型却输出

        natural matte skin with pore-level texture; fine individual hair strands
        with flyaways; soft layered feathers…; detailed eyes with iris fibres;
        the soft sheen of the lips

    这段话是会被模型**真的照着画上去**的——等于往墙上画皮肤和嘴唇。
    所以它不是「读图不准」，而是内容污染，必须挡住。

    现在的做法是两道保险：
      · 提示词改成「两步走」：先让模型在 surfaces_seen 里用中文写出它在这张
        图里**真正看到**的表面，再把这些条目逐条译成英文；并明确告诉它
        「手绘 / 壁纸 / 绘画 / 风景画面里没有皮肤、没有头发、没有嘴唇」，
        词典是查词用的，不是答案。
      · 代码机械复检：照抄的回答会**顺着词典的行号一路往下走**（真看图的
        回答按画面占比排序，和词典行序无关）。检测到这种轨迹就把错误贴回
        去重问一次；再抄就直接报错，绝不把这份提示词交给你。
        注意判据**不是**「用了词典措辞」——用词典措辞本来就是这一档的设计
        意图，所以完全正确的回答不会被误杀。

  ── 坑二：漏材质（尤其是植物和花）──

    这一档**故意不写主体名**（不写「孔雀」「这只鸟」），因为块数多的时候
    点名主体会让模型把孔雀幻觉进不含它的块里。但「不写主体」≠「不写材质」：
    **占画面大宗的材质一条都不能漏**，否则那些 tile 就完全没有指引。

    实测报过的例子：图是「植物、树木、花、鸟」，输出却只有

        flat painted pigment fields with their brushwork; wood-grain texture;
        soft layered feathers with their barbs and downy texture

    → 植物和花全丢了；而且 `wood-grain texture` 是**木料**（家具、地板、
       画框）用的，活树不该用它，活树要写 `leaves, bark, and twigs, …`。

    修法：词典补上「花瓣 / 花朵」「草 / 地被 / 苔藓」两行，把活树的
    「枝叶 / 树皮 / 枝桠」和「木料 / 木板」明确拆开；规则里加一条
    「占画面大宗的材质一条都不能漏」；提示词里也补了这个具体反例。

    正确应该长这样（底色 + 一条 painted …）：

        flat painted pigment fields with their brushwork; painted foliage,
        flowers, and plumage

    ⚠ 如果你希望提示词里**明确出现**「植物」「花」「鸟」这些词，texture 档
      做不到——这是仓库给这一档的定位（它只写材质表面，不写主体）。
      改用 **full_build 档**（把 tile 调大、块数压到 6 块以内）就会逐条
      点名主体和材质。

  ── 坑三：给「画出来的东西」加真实材质的微观结构 → 出图偏离原图 ──

    坑二修过头了。为了补上漏掉的植物和花，我把画出来的花鸟树石按**真实材质**
    写了：

        flat painted pigment fields with their brushwork; wood-grain texture;
        leaves, bark, and twigs, each its own texture;
        soft petals with their delicate surface and fine veining

    `bark`（树皮）、`veining`（叶脉）、`barbs`（羽枝）这类词是「请给我写实
    微观结构」的请求。源图是平涂手绘时，模型会照着在画面上**叠一层写实材质**
    ——给画出来的花加叶脉、给画出来的树加树皮——出图就不像原图了。

    实测反馈：「没改之前的提示词好，生成的图片更符合原图」——说的就是这一版。

    修法：
      · 词典新增一条「画出来的花鸟树石（手绘 / 印刷图案本身）→ painted
        foliage, flowers, and plumage」，画出来的东西一律写 painted …；
      · 提示词加一整节【整幅是画 / 印刷品时】，写明**保真优先于描述详尽**，
        并禁止给画出来的东西安 bark / barbs / downy / veining / wood-grain；
      · 花瓣那行去掉 `and fine veining`；
      · 底色那行**保留** `with their brushwork` —— 它是「保住平涂笔触」的
        信号，不是发明许可证；拿掉反而会让底色被当照片处理。

    → 通用规则：**画面本身是画，就给「画出来的」措辞；画面是照片，才用写实
      措辞。** 判定很简单：整幅画面里没有一处真实材质的微观结构，那它通篇
      都是「画出来的」。

    万一模型还是写得太「写实」，提示词框是**可以直接改的**——把中间那段
    材质普查换成上面那句短的，再拿去跑即可。

    所以万一看到「模型连续两次都把材质词典当答案抄了回来」的报错，
    那不是后端坏了，是模型偷懒。两个办法：
      · 换一个更强的视觉模型；
      · 或者把 tile 调大、把块数压到 6 块以内，改用 full_build 档——
        那一档是逐条点名「材质 + 子特征 + 正向守卫」，对弱模型友好得多。

  三个档位的「中间段」长度不一样，这是仓库的规定：
    full_build（≤6 块）  → 变量块 2~7+10 全都写，最详细
    texture（7~24 块）   → 只填一个材质普查槽位，不点名主体
    subject_less（>24 块）→ 只填材质族，去掉所有主体名防幻觉
  所以块数一改，记得重新生成提示词。


【模型填得不好时，工具会自动兜哪些底】

固定块是逐字照抄 md 的，改不了；能出问题的只有「变量槽位」。
视觉模型偶尔会把槽位填歪，工具会做四种处理 —— 前两种**自动修**，
后两种**只提醒**（因为它修不了，得你决定）：

═══ ① 槽位写成整句 → 自动改成名词短语 ═══

模板要的是名词短语，但模型有时写成整句，直接拼进去就是破碎英文：

    模型给        there is a marble counter / it is shallow / bokeh is soft
    旧版拼出来    Keep the there is a marble counter naturally detailed within
                  its existing it is shallow, holding the bokeh is soft as …
    现在拼出来    Keep the marble counter naturally detailed within its
                  existing shallow, holding the soft bokeh as …

处理三种情况：切掉 `there is / it is / this is` 这类开头；把
`bokeh is soft` 这种「主语在前」的翻回 `soft bokeh`；去掉槽位尾部的句号
（否则会把句子劈成两半）。

⚠ **翻不动的不会硬翻。** 只有尾部是**短形容词短语**才翻；含介词或分词
（比如 `the light is coming from the left`）会原样保留，改在自检里提醒你
「这块看起来是整句」。硬翻会变成 `coming from the left light`，比不翻更糟。

═══ ② 完全重复的内容 → 自动去重 ═══

同一条材质写两遍、同一条精细元素写两遍，会输出两句一模一样的话 ——
纯冗余，还会把同一个概念重复加权。工具会去掉重复的那条，**并告诉你去掉了
几条**（静默去重同样是「看不出来发生了什么」）。

注意：**同一材质但子特征不同**（比如 `polished steel armour` 一条写
`rivets`、一条写 `plate seams`）**都保留**，只提醒你「合成一条更紧凑」——
因为合并会丢掉其中一条的子特征，这个取舍该你来定。

═══ ③ environment 缺槽位 → 提醒（这是最容易被忽略的一条）═══

environment 有四个槽位（background / depth / soft_elements / state）。
模型只填了 background 时，组装器**不会让句子出现空位**，会补上通用词：

    Keep the produce and shelving naturally detailed within its existing
    depth, holding the soft gradients as soft and intact.

`depth` / `soft gradients` / `soft and intact` 都是通用填充，而 md 写作
规则 6 恰恰要求删掉这种「没点名具体东西的措辞」。旧版**不提醒**，你根本
分不清这句是模型写的还是工具补的 —— 现在自检会明确说「缺了哪几个槽位、
已经用通用词顶上」，看到就该重新生成。

═══ ④ 用了 md 禁用动词 → 提醒 ═══

md 写作规则 2 明确禁用四个「变换类动词」：

    enhance / improve / make better / fix

它们会把模型推离源图（模型会去「改造」而不是「恢复」）。旧版漏检 `fix`，
现在四个都查。注意是按**词边界**匹配 —— `prefix` / `suffix` / `fixture`
里的 fix 不算违规（旧版用子串匹配，加上 fix 就会误报）。

═══ 另外：模型也被明确告知了这些规矩 ═══

上面是「模型不守规矩时怎么兜」。预防那一边也补了：给模型的系统提示里，
environment 那节现在明确写着「四个字段都填名词短语，不要写成整句
（别出现 is / are / there is）」。


【提示词里的 Image 1 / Image 2 / Image 3 是什么】

这是最容易被误判成 bug 的一处。

症状：左边图片列表里**只放了一张图**，生成的提示词开头却是

    Image 1 is the tile to refine — resolve fine detail and crisp, clean
    edges across image 1 only, as a high-resolution delivery master of …
    Image 2 shows where this tile sits within the full frame;
    image 3 is the full source photo — draw on images 2 and 3 only for
    matching colour, lighting, and edge continuity …

于是很容易怀疑：是不是没清除干净？是不是工具把以前的图串进来了？

不是。这句话里的三个 image **不是你的图片列表**，而是 ComfyUI 在
现场从你那**一张**图里切出来的三路参考：

    提示词里写的      ComfyUI 节点里的名字    实际是什么
    ─────────────────────────────────────────────────────────────
    Image 1          tile_latent        这个块自己那一块裁切 —— 要修的就是它
    Image 2          position_latent    这个块在全图位置图里的那一格
    image 3          global_latent      整张放大图缩到 768px 的缩略图

翻译成人话，提示词是在交代任务分工：

    1 号 = 要精修的主体（内容只能从它出）
    2 号 = 告诉你「这一块原本在画面哪个位置」
    3 号 = 告诉你「整幅画该是什么色调」
    2 号和 3 号只准拿来对颜色 / 对光 / 对边缘连续性，不准拿内容。

三路参考的编号顺序是节点定死的：Flux2KleinRefLatentWeight 的
reference_index 0 / 1 / 2 依次对应 tile_latent / position_latent /
global_latent。工具生成的「ComfyUI 设置说明」页里也是按这个顺序列的，
那里还写了三路各自的权重。

═══ 它什么时候出现、什么时候不出现 ═══

要**同时**满足两个条件才会出现：

  条件一：档位是 full_build（块数 ≤ 6）
  条件二：参考形态是「三参考」

两个条件的实测结果（逐档 × 逐形态跑了一遍，不是看代码猜的）：

    档位            参考形态    提示词里有没有 Image 编号
    ─────────────────────────────────────────────────────
    full_build      三参考      ✅ 有 Image 1 / Image 2 / image 3
    full_build      单参考      ❌ 没有，开头换成 OPEN_SINGLE
    texture         三参考      ❌ 没有（这一档根本不用那个模板）
    texture         单参考      ❌ 没有
    subject_less    三参考      ❌ 没有
    subject_less    单参考      ❌ 没有

原因：只有 full_build 那一档的模板带这三个 image 的说明。另外两档
（texture / subject_less）的模板里**一个 "Image" 都没有**，开头是

    「RFNTILE. refine and add detail to this upscaled tile. Restore the
      image quality and resolve it to a sharp, high-resolution result. …」

所以如果你**现在**看到提示词里有 Image 1/2/3，说明生成那一刻块数 ≤ 6
（也就是 tile 开得很大，比如 2560 / 2816 / 3048 那种，一张图只切 2 块）。
块数一改（tile 调小），档位掉到 texture，这三个 image 就自动消失了 ——
所以改完 tile 一定要重新生成提示词。

单参考形态下（无论哪档）都没有 Image 编号，开头是

    「RFNTILE. refine and add detail to this upscaled tile. Finish this
      image as a high-resolution delivery master. Resolve fine detail and
      crisp, clean edges throughout …」

代价是丢掉位置图和全局图的约束，块与块之间更容易出现颜色不接
（见【为什么会有塑料感 / 为什么色调越来越暗】里的颜色校正那一段）。

界面上现在有两处直接写着这个映射，不用回来翻文档：
  · 「参考形态」下拉的选项文字本身就带着 image1/2/3 的对应关系
  · 提示词框上方那行小灰字，跟着「参考形态 + 档位」实时变 ——
    三参考 + texture 档时它会改口说「本档提示词没有 Image 编号」，
    免得你去满篇找一个不存在的词

═══ 我自己怎么查这件事 ═══

三步，全在界面上，不用翻文档：

  1. 看「提示词」页签的标题。如果是「提示词 ⚠ 参数已改」，
     说明这份提示词是按**旧参数**生成的，档位可能早变了 —— 直接重新生成。
  2. 看右上「关键数字」区里「提示词档位」那一行：

       full_build  · 完整构建   → 提示词里**会**出现 Image 1/2/3
       texture     · 材质普查   → **不会**出现
       subject_less · …         → **不会**出现

  3. 看「生成提示词」按钮右边那行小灰字，它会直接告诉你这一档有没有编号。

如果你手上那份提示词里有 Image 1/2/3，而第 2 步显示的是 texture ——
那就是第 1 步那种过期情况：中途改过 tile 却没重新生成。点一次
「生成提示词」就对齐了。

═══ 那「清除」到底有没有用 ═══

有用。实测（载入真实图片 → 生成过提示词 → 点「清空列表」）：

    图片列表        1 张          →  0 张
    当前选中        有            →  无
    提示词框        有字          →  空
    设置说明框      有字          →  空
    「提示词」页签   带 ⚠ 提示     →  回到「提示词」
    预览            ← 回到「未选择图片」
    八个关键数字     ← 全部回到「—」

唯一**故意不清**的是参数区（tile / 重叠 / 参考形态 / cell_size …）——
那些是你的偏好，不是某张图的属性，换图时不该被重置。

结论：只放一张图 + 提示词里有 Image 1/2/3 = 正常现象，不是残留，
也不是没清干净。


【三参考和单参考有什么区别，怎么选】

═══ 先说最容易误解的一点 ═══

这个下拉**只改提示词怎么写**，它**不会**去改你的 ComfyUI 工作流。

真正的区别在 ComfyUI 那边：这个块采样时，到底喂了几路参考图进去。

    三参考 = 喂 3 路：tile_latent + position_latent + global_latent
    单参考 = 只喂 1 路：tile_latent

工具按你选的这一项，把提示词写成对应的说法（三参考会点名 Image 1/2/3，
单参考只说 this image）。所以：

    ⚠ 选哪个，取决于你的 ComfyUI 工作流**实际接了几路**。
      两边对不上，提示词就是在跟模型说瞎话。

═══ 三路各自是干什么的 ═══

    Image 1 = tile_latent     这个块自己的裁切   → **内容**全靠它
    Image 2 = position_latent 这个块在全图位置图里的那一格 → 位置 / 边缘接续
    Image 3 = global_latent   整张放大图的缩略图 → 整幅该是什么**颜色和光照**

提示词里那句原文写得很明确：draw on images 2 and 3 **only** for matching
colour, lighting, and edge continuity —— 也就是说，2 和 3 不提供内容，
只负责「让这一块跟全图看起来是一张图」。内容永远只从 image 1 来。

═══ 怎么选 ═══

**默认就用三参考。** 官方示例工作流接的就是 3 路，而且那两路正是治
「跨块偏色」的：模型每画一块都能看到「整幅该是什么色调」的参考，
块与块之间才不容易各画各的。

**只有这两种情况才改单参考：**

  1. 你明确改过工作流，只接了一路参考（比如为了省显存 / 提速）；
  2. 你在做实验，想对比「有没有全局参考」对偏色的影响。

═══ 选错了会怎样 ═══

    工作流接 3 路，但你选了单参考
      → 提示词不提 Image 2/3，模型不知道那两路是干嘛的，
        全局颜色锚定基本白接。**跨块偏色会更明显。**

    工作流只接 1 路，但你选了三参考
      → 提示词叫模型「draw on images 2 and 3」，可那两路根本不存在。
        轻则指令落空，重则模型自己脑补出源图里没有的东西。

所以改完这个下拉，**记得重新点一次「生成提示词」**（页签会显示 ⚠ 参数已改）。
另外「ComfyUI 设置说明」页也会跟着变：选单参考时它会写成
`Flux2KleinRefLatentWeight × 1`，并明确标出位置图 / 全局图那两路不接 ——
照那份清单接线就不会错。


【为什么会有塑料感 / 为什么色调越来越暗】

这两个问题都不是「提示词写错了」，一个是提示词**目标定反了**，
一个是流程里**缺一步颜色校正**。分开说。

═══ 一、塑料感：提示词把目标定成了「照片」═══

这一档的固定话术里有四句，对「手绘 / 印刷」源图是**反的**：

  Remove compression artifacts, banding, and noise
    纸纤维、颜料颗粒、笔触的毛边，在模型眼里就是 noise —— 被抹掉。
    而纸纤维正是手绘壁纸的命根子。
  clarify soft or blurred areas into crisp, clean edges and definition
    手绘的软边被硬化成数码锐边。
  leave flat or evenly-toned areas clean and smooth
    粉底被擦成一张光滑的塑料面。
  Produce a clean, photorealistic result faithful to the source
    目标被定成「照片」，而源图是**画**。

四句合起来的效果就是：纸纤维没了、笔触没了、哑光颜料颗粒没了，
只剩一层光滑均匀的表面 —— 这就是「塑料感」。

而且这一档**没有任何一句「保持手绘感」**。仓库里唯一提到手绘的是
`full_build_upscale_prompt.md` 的 painterly 变体：

  Block 1 加：..., while preserving its painterly, concept-art rendering
              and brushwork
  Block 10 用 Style 标签：Style: oil painting.
  并且把皮肤那块的 pore-level 去掉

—— 这些只写在 full_build 模板里。texture / subject_less 档和标准提示词
里一个字都没有，所以没有任何东西在拦它往照片方向跑。

按**风险从低到高**试（前两条是纯数值，不碰提示词）：

  1. 调高三个 RefLatentWeight
       tile 0.9 → 1.0，position 0.8 → 0.9，global 0.8 → 0.9
     官方便签原文：Lower values give higher creativity but can lower
     resemblance. 调高 = 更贴源图、更少自由发挥、更少「发明」。
  2. ctrl3_max_size 768 → 2048（见下一节的说明）
  3. 让**材质普查那一段**去承担「这是画」这个信息，例如写成
       flat painted pigment fields with their brushwork
     —— 这是唯一不违反仓库「只有普查段可变」这条规矩的写法。
     （本工具的 texture 档已经会这么写了。）
  4. 还不行就走 full_build 档：把 tile 调大、块数压到 6 块以内，
     那一档有仓库官方的 painterly 子句和 Style: 标签可用。

═══ 二、色调越来越暗 / 每次都不一样 ═══

四个原因叠在一起，**没有一个能单独背这个锅**：

1. 【流程本身不校正颜色】每个 tile 都是**从纯噪声重画**的，只靠三路
   参考 latent 约束。整条流程里**没有任何一步**把颜色拉回源图。
   而 Hildegard Combine 是「后画的盖住先画的」（source-over，不是加权
   平均）：源码里羽化带从 overlap/4 处才开始、模糊半径 = sqrt(overlap)，
   于是重叠的 512px 里只有约 44px 在做真正的交叉淡入。
   块与块之间那点色调差不会被抹平，会留下色带。

2. 【官方解药默认是关着的】工作流里有个 `Flux2KleinColorAnchor` 节点，
   官方示例里是 **BYPASS** 状态。官方便签原文：
     If you see color drifts between tiles you can activate the color
     anchoring node.
   它是第三方节点（ComfyUI-Flux2Klein-Enhancer），作用是拦住模型每一步
   的 x0 预测，把每通道的均值往参考 latent 的均值上拉。

   开它要**三个动作，缺一个都跑不起来**：
     a. 选中节点 → Ctrl+B（或右键 Set Mode → Always）取消 BYPASS
     b. **把 conditioning 接上** —— 它是**必填输入**，官方示例里空着
        （link: null）。直接取消 BYPASS 只会报「缺输入」。接最后一个
        ReferenceLatent 的输出（官方示例里是节点 8）即可。
     c. ramp_curve 从默认 1.5 调到 **2~4** —— 节点自己的说明写着
        For few-step schedules (4-8 steps) values of 2-4 work well，
        本流程正是 4 步。
   strength 保持 0.5（说明里 0.3-0.6 是推荐区间）。
   ref_index 保持 0 = 锚在 tile_latent，也就是本块自己的裁切 ——
   正好是「每块都跟自己对得上的源图区域」那一路参考。

3. 【每次都不一样 = 种子在变】RandomNoise 节点的 seed 控制默认是
   `randomize`，每次排队种子都不同。想比对效果，先把它改成 `fixed`。

4. 【每多跑一趟就暗一档】仓库建议分 2~3 趟放大。但每一趟都要
   重新 VAE 编码一次、重画一遍，偏色会**累加**。这就是「每次都会暗
   很多」的放大器。趟数越少越稳。

顺带一个容易被忽略的：`ctrl3_max_size` 官方示例填的是 **768**，
而节点自身的默认是 **2048**。768 表示全图缩略参考只有 768px ——
模型对「整幅应该是什么色」的印象很粗，更容易漂。调到 2048 试试。

→ 一句话总结：
   塑料感 = 提示词把「去噪 + 锐化 + 平滑 + 照片」当成了目标；
   变暗   = 没人管颜色（锚定节点关着）+ 种子在变 + 趟数在累加。


【几个必须知道的坑】

1. min_scale_factor 只是「下限」，不是实际倍数。
   真实倍数会被 tile 网格向上取整吸附。
   例：1024×1536 的图，你填 1.0 / 1.3 / 1.5 / 2.0，结果全都是 2048×3072（2.0×）。
   想更接近目标倍数，用试算表换个 tile 尺寸试。

2. tile 尺寸的选择会直接改变最终倍数。
   同一张 1024×1536：tile=1536 得 1.5×，tile=2048 得 2.0×，tile=1024 变 8 块 1.75×。

3. 块数 = 云上采样次数。块数多不只是慢，费用也高。
   工具会在设置说明里标出来。

4. 网格算成 1×1 时，整条流程退化成单张精修，没有拼缝问题，
   Hildegard Combine 实际不起作用。

5. 提示词档位是自动判的（按块数）：
   ≤6 块    → full_build   逐元素点名材质，最激进
   7~24 块  → texture      退到材质普查，不点名主体
   >24 块   → subject_less 去掉所有主体名，防幻觉
   如果 AI 看到「密集重复主体」或「大面积空白」，会自动改成 subject_less。
   拿不准时选更保守的那档——多块时点名主体会被幻觉进不含它的块里。

6. 提示词里的固定块（触发词、clean-up、scope lock）是代码逐字写死的，
   不是 AI 自由发挥。AI 只填变量槽位。这样 LoRA 的训练信号不会被改写。

7. 官方建议：分 2~3 次小幅（每次约 2×）放大，别一次跳 4~8×。

8. 本地模型报「输出被截断了」= LM Studio 的 Context Length 太小。
   报错里会直接告诉你去哪里调。调完点「测试连接」确认。
   云端 API 不会遇到这个问题（上下文都很大）。

9. 最小重叠不只是「接缝软不软」——它和 tile 尺寸一样会改变输出尺寸和块数。
   而且新建的 Hildegard Plan 节点 min_overlap 默认是 1/32 Tile、
   min_scale_factor 默认是 3.0，和工具里的 1/4 Tile / 1.3 不一样，
   直接拖个新节点不改参数，输出尺寸会对不上。详见【最小重叠是什么】。

【提示词为什么能保证跟作者的 md 一致】

  templates.py 里的固定块是**从 md 里逐字抄下来的**，只有槽位（{…} 那些）
  会随图片内容变化。为了让这件事可验证、而不是靠人眼，做了两层保险：

  1. llm_prompt_templates/ 把作者仓库的三份 md 原文存了下来。以前只存在
     我这边，你换台机器就没人能核对；现在它是随工具一起走的。
  2. md_conform.py 自动对账 —— 把 md 里的固定措辞和 templates.py 里的常量
     逐块比，md 有而代码没有、或代码多出 md 没有的，都会列出来。
     自检 [13] 就是跑它。改过 templates.py 之后如果 [13] 报错，
     说明提示词已经跑偏了。

  换句话说：以后「提示词跑偏」不用再靠对比出图效果来发现，跑一次自检
  就能定位到是哪一块、哪个措辞对不上。
